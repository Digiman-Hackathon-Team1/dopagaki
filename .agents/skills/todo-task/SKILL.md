# todo-task

진행 상황과 작업 설명의 기준은 GitHub 이슈(`Digiman-Hackathon-Team1/dopagaki`)다. 설계는 노션 설계 문서에 있다. 이 순서를 따른다.

## 1. 최신 상태와 사용자 확인

1. `git switch develop && git pull --ff-only`로 최신 `develop`을 받는다. 작업 중인 변경이 있으면 먼저 사용자에게 알린다.
2. 사용자가 누구인지 확인한다: `gh api user -q .login` 또는 `git config user.name`.

| GitHub 로그인 | 이름 |
|---|---|
| baekyutae | 배규태 |
| morishjs | 박준석 |
| uponinon | 이우진 |

황인식·손창현·백락원 님은 GitHub 로그인을 아직 받지 않았다. 표에 없으면 사용자에게 이름을 묻는다. 로그인을 추측해서 표에 넣지 않는다.

## 2. 내 작업 보여 주기

1. 내 이슈를 가져온다: `gh issue list --assignee <로그인> --state open --json number,title,body`
2. 이슈 제목에서 작업 번호(`T1`)와 우선순위(`[P0]`)를 읽는다.
3. **선행**은 이슈 본문 `## 의존`의 이슈 번호(예: `T1 #4`)로 판단한다. `gh issue view <번호> --json state -q .state`가 `CLOSED`이면 끝난 것이다. `## 의존`이 없으면 선행이 없다. "병렬 가능"처럼 덧붙인 말이 있으면 함께 보여 준다.
4. 표로 보여 준다: 작업 · 이슈 · 우선순위 · 선행(이슈 번호와 끝났는지).
5. 인자로 작업 번호(예: `T1`)를 받았으면 그 작업으로 바로 간다. 아니면 **P0이고 선행이 끝난 작업** 중 작업 번호가 가장 작은 것을 추천하고 확인받는다.

## 3. 작업하기

1. 노션 설계 문서 전체를 먼저 읽는다: https://app.notion.com/p/423bf371be2d803288d0d8e8819739d4
2. 고른 이슈 본문의 **목표 · 범위 · 완료 기준 · 의존**을 읽는다. `## 시작 전`이 있으면 그것부터 한다. 이슈 "참고"에 적힌 장을 이번 작업의 기준으로 삼는다.
3. `develop`과 `main`에는 직접 push하지 않는다. `develop`에서 브랜치를 만든다. 이름은 `docs/git-naming-convention.md`를 따른다: `git switch -c <type>/<이슈번호>-<slug>` (예: `feat/5-search-clinics`).
4. 작업 범위는 이슈 "범위"로 제한한다. 범위에 없는 기능, 리팩터링, 다른 사람 담당 영역(다른 앱, 다른 담당의 파일)을 바꿔야 할 것 같으면 멈추고 사용자에게 알린다.
5. 설계 문서와 이슈가 다르면 설계 문서를 따른다. 판단이 서지 않으면 멈추고 묻는다.
6. 설계를 바꿔야 하면 사용자에게 알리고, 승인받아 설계 문서를 고치면 하위 페이지 "설계 변경 기록"(https://app.notion.com/p/424bf371be2d81dda111e3a9b4583311)에 한 건 남긴다. 형식은 버전·날짜 제목 아래 변경 전, 변경 후, 이유, 근거, 관련(ADR·PR·이슈). 선택지를 비교한 큰 결정은 `docs/adr/`에도 남긴다.
7. 작업 규칙은 루트 `AGENTS.md`와 `apps/api/AGENTS.md`를 따른다.

## 4. 완료 기준 확인

1. 완료 기준을 하나씩 확인하고 결과를 기록한다.
2. 실제 Claude로 확인하는 항목은 직접 돌려 본 결과(입력과 응답 요지)를 적는다. 돌려 보지 못했으면 그렇게 적는다.
3. `pnpm check`와 `pnpm build`를 통과시킨다. 테스트 통과만으로 완료 처리하지 않는다.
4. API 요청·응답을 바꿨으면 `pnpm generate` 결과를 같은 PR에 포함한다.

## 5. PR 올리기

1. 커밋 메시지는 `docs/git-naming-convention.md`를 따른다: `<type>(<scope>): <요약> (#<이슈번호>)` (예: `feat(agent): search_clinics 도구 추가 (#5)`). 작업 단위별로 나눠 커밋한다.
2. PR 본문은 아래 양식으로 쓴다. 이슈 완료 기준을 하나씩 대조해 "검증" 또는 "남은 것"에 빠짐없이 넣는다.

   ```markdown
   ## 요약

   왜 하는 작업인지 문제 상황부터 쓴다(무엇이 안 됐고, 어디서 왜 막혔는지).
   이어서 이 PR이 무엇을 하는지 한두 문장으로 쓴다. 바꾸지 않은 것이 있으면 함께 밝힌다.

   - base: `develop`
   - 설계 기준: 노션 설계 문서의 해당 장, 원자료가 있으면 링크 또는 경로

   ## 주요 작업 단위

   ### 1. <무엇을 했는지 한 줄>

   - 바꾼 것을 컴포넌트·파일·함수 이름과 함께 쓴다
   - 왜 그렇게 했는지, 다른 파트에 영향이 있으면 누구와 맞출지 적는다

   ## 검증

   - 실제로 돌려 본 것만 적는다: 테스트 개수, 실행 명령, 실제 Claude로 확인한 입력과 응답 요지
   - 확인하지 못한 것은 못 했다고 적고 이유를 쓴다

   ## 남은 것

   - 이번 범위에서 뺀 것, 후속으로 정할 것

   Closes #<이슈번호>
   ```

   - 문체는 "~한다"로 쓴다.
   - 표는 전후 비교처럼 숫자를 대조할 때만 쓴다. 측정값이 있으면 "검증" 앞에 `## 측정 결과`를 둔다.
   - 작업 단위는 리뷰어가 읽는 순서대로 번호를 붙인다.
   - 멘션(@)은 사용자가 요청할 때만 넣는다.
3. 사용자에게 확인받은 뒤 브랜치를 push하고 PR을 연다. 제목은 `<type>(<scope>): <요약> [T<번호> #<이슈번호>]`: `gh pr create --base develop --title "feat(agent): … [T2 #5]" --body-file …`
4. CI(`check`)가 실패하면 고쳐서 같은 브랜치에 다시 push한다.
5. 머지는 사용자가 요청할 때만 한다. 머지 커밋으로 머지하고(`gh pr merge --merge`, Squash 아님), 자동 머지(`gh pr merge --auto`)는 쓰지 않는다. 이슈는 PR이 `develop`에 머지되면 `Closes`로 닫힌다.
6. PR 본문을 고칠 때 `gh pr edit`은 이 레포에서 실패할 수 있다. `gh api -X PATCH repos/Digiman-Hackathon-Team1/dopagaki/pulls/<번호> -F body=@<파일>`로 고치고 반영됐는지 확인한다.

## 하지 않는 것

- 완료 기준을 확인하지 않고 완료라고 하지 않는다. 확인하지 못했으면 그렇게 말한다.
- 노션 설계 문서에 진행 상황을 적지 않는다(설계 문서다). 설계를 바꿔야 하면 사용자에게 알린다.
- 설계 문서를 고치고 설계 변경 기록을 빠뜨리지 않는다.
- 작업 번호(T번호)를 바꾸거나 다시 쓰지 않는다.
- 다른 사람에게 배정된 이슈를 대신 진행하거나 닫지 않는다.
