# [ADR-0003] 에이전트 응답 형식을 칸으로 고정하고 구조화 출력으로 보장

* **상태 (Status):** 제안됨(Proposed). 카드 형식은 프론트(황인식·손창현 님)와 합의 필요
* **날짜 (Date):** 2026-11-26
* **관련 (Related):** T0 #3, T2 #5(제외 사유 칸 추가)

## 1. 배경 및 문제 상황 (Context and Problem Statement)

* **상황:** 에이전트 응답에는 본문 말고도 병원 카드, 질문 선택지, 다음 질문 제안, 주의사항이 함께 나간다(설계 문서 4.8). 프론트는 이것들을 각각 다른 화면 요소로 그린다.
* **문제:** LLM이 자유 텍스트로 답하면 프론트가 카드와 선택지를 텍스트에서 찾아내야 하고, 형식이 조금만 어긋나도 화면이 깨진다.
* **목표:** 프론트가 칸마다 화면을 따로 그릴 수 있게, 응답 형식을 정해진 칸으로 고정하고 그 형식을 항상 지키게 한다.

## 2. 고려한 옵션들 (Considered Options)

### 1. 응답을 정해진 칸으로 고정하고 구조화 출력으로 보장

응답을 아래 칸으로 나눈다. 형식은 Claude API의 구조화 출력(`output_config.format`)으로 보장한다.

| 칸 | 내용 |
| --- | --- |
| 조건 요약 | 이해한 조건 한 줄 |
| 답변 | 본문 (표, 목록 사용 가능) |
| 카드 | 병원 추천, 일본 시술명 대응, 예약 채널 등 |
| 제외 사유 | 거르기로 빠진 병원 수(사유별: 바늘, 회복 기간, 지역, 일본어, 예산). 설계 v1.2에서 추가(ADR 0004, 0009) |
| 질문 묶음 | 먼저 물어야 할 때의 질문과 선택지 |
| 다음 질문 제안 | 3개 |
| 주의사항 | 모르는 조건, 약한 근거 |
| 기억할 조건 | 사용자가 직접 말한 조건. 화면에 보내지 않고 코드가 검사해 사용자 기억에 저장한다. 설계 v1.11에서 추가(ADR 0019) |

**Pros**
* 프론트가 칸마다 화면을 따로 그릴 수 있다.
* 칸 스키마가 Pydantic DTO → OpenAPI → `@repo/api-client`로 web 타입이 된다.
* 형식 오류를 API가 막아 준다.

**Cons**
* 칸이나 카드 종류를 바꾸면 DTO와 web을 함께 바꿔야 한다.
* 카드 형식을 프론트와 먼저 합의해야 한다.

### 2. 자유 텍스트에서 카드를 파싱

LLM이 텍스트로 답하고, 서버나 프론트가 텍스트에서 카드와 선택지를 찾아낸다.

**Pros**
* 스키마 합의 없이 바로 시작할 수 있다.

**Cons**
* LLM 출력 형식이 조금만 달라져도 파싱이 실패해 화면이 자주 깨진다.
* 카드 속 금액이 도구 결과와 같은지 검증하기 어렵다.

## 3. 결정 사항 (Decision Outcome)

* **응답을 정해진 칸으로 고정하고 구조화 출력으로 보장하는 안을 제안한다.**
* **자유 텍스트에서 카드를 파싱하는 방식은 채택하지 않는다.**
* **prefill(응답 앞부분을 미리 채우는 방식)은 쓰지 않는다.** Sonnet 5.5와 Haiku 5.5에서 assistant prefill은 400 오류를 반환한다.

**이유**
* 프론트가 칸마다 화면을 그리려면 형식이 항상 같아야 한다.
* 형식 보장 수단 중 prefill은 후보 모델(Sonnet 5.5, Haiku 5.5)에서 쓸 수 없고, 구조화 출력은 쓸 수 있다.
* 카드의 금액을 도구 결과와 대조하는 숫자 검증(설계 문서 12장)이 칸 단위로 쉬워진다.

**후속 작업**
* 황인식·손창현 님과 카드 형식(설계 문서 4.8 초안) 합의
* T1 #4 응답 DTO 최소 형태
