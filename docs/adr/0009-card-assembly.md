# [ADR-0009] 추천 카드는 도구 결과로 조립하고, LLM은 추천 이유만 쓴다

* **상태 (Status):** 채택됨(Accepted). 카드 필드는 프론트(황인식·손창현 님)와 합의 필요
* **날짜 (Date):** 2026-11-26
* **관련 (Related):** T2 #5, ADR 0003, 설계 문서 4.7·4.8·9장

## 1. 배경 및 문제 상황 (Context and Problem Statement)

* **상황:** 응답에는 병원 추천 카드(가격, 엔화 환산, 일본 대비 절약액, 추천 이유)가 들어간다(설계 문서 4.8). 금액은 `search_clinics`가 계산하고, 추천 이유는 LLM이 한 줄씩 쓴다(4.7).
* **문제:** 카드의 금액을 누가 채울지 정해야 한다. LLM이 도구 결과를 옮겨 적으면 숫자를 틀리게 쓸 수 있고, 그러면 카드가 web 순위표와 달라진다.
* **목표:** 카드 금액과 순서가 항상 도구 결과와 같고, LLM은 카드마다 추천 이유를 쓴다.

## 2. 고려한 옵션들 (Considered Options)

### 1. 도구가 카드 데이터를 따로 넘기고, LLM은 카드 ID별 이유만 쓴다

도구는 LangChain `content_and_artifact`로 두 가지를 돌려준다. `content`는 LLM이 읽는 요약 문장이고, `artifact`는 카드 데이터다. 카드 데이터는 LLM에 보내지 않는다. LLM은 응답 칸 `card_reasons`에 카드 ID와 이유만 쓰고, `finalize`가 둘을 합친다.

**Pros**
* 카드 금액이 구조상 도구 결과 그대로다. 설계 원칙 "금액은 도구 결과만"을 코드가 보장한다.
* LLM 출력이 짧아 응답이 빠르고 비용이 적다.
* 설계 문서 9장("도구는 LLM에는 요약, 화면에는 카드 데이터를 따로 넘긴다")과 같다.

**Cons**
* 카드에 넣을 수 있는 정보가 도구가 준 것으로 한정된다.
* 카드를 조립하는 코드(`assemble_cards`)가 필요하다.

### 2. LLM이 카드 JSON 전체를 쓴다

응답 칸에 카드 칸을 두고, LLM이 도구 결과를 보고 금액까지 채운다.

**Pros**
* 구현이 단순하고, LLM이 카드 내용을 자유롭게 구성한다.

**Cons**
* LLM이 금액을 잘못 옮겨 적을 수 있다. 막으려면 카드 금액을 도구 결과와 대조하는 검증과, 틀렸을 때의 처리가 따로 필요하다.
* 출력이 길어져 응답이 느려진다.

## 3. 결정 사항 (Decision Outcome)

* **도구가 카드 데이터를 따로 넘기고, LLM은 카드 ID별 이유만 쓰는 방식을 선택한다.**
* **LLM이 카드 JSON 전체를 쓰는 방식은 채택하지 않는다.**
* **보여 줄 카드도 LLM이 고르게 하는 방식(이유를 붙인 카드만 표시)은 채택하지 않는다.** 설계 문서 4.7은 상위 3곳을 보여 주고 LLM이 이유를 붙이는 것이고, 몇 곳을 보여 줄지는 4.5 역할표상 코드 쪽 판단이다. 이유를 빠뜨리면 카드가 사라지는 문제도 있다.

조립 규칙(`api/agent/graph.py`의 `assemble_cards`)

* 이번 턴(마지막 사용자 메시지 뒤)의 결과만 쓴다. 이전 턴의 카드 ID를 다시 써도 카드는 나가지 않는다.
* 성공한 `search_clinics` 결과의 카드는 모두 내보낸다. 다른 도구의 결과와 오류 난 호출은 읽지 않는다.
* 같은 턴에 같은 시술을 다시 검색하면, 비교인지 범위를 좁힌 재검색인지를 검색 조건(`SearchTarget`)으로 가른다.
  * 지역·기준 위치·지점 이름을 서로 다르게 지정했으면 비교로 보고 앞 결과도 남긴다. 예: "밴스 홍대"와 "블리비 명동", 홍대와 강남.
  * 한쪽만 지정했거나 같거나 지점 이름이 더 좁아졌으면 재검색으로 보고 앞 결과를 지운다. 예: 전체 → 강남, 전체 → 일본어 가능만, "밴스" → "밴스 홍대".
  * 비교 결과에 같은 병원이 두 번 나오면 처음 것만 남긴다. 다른 시술 검색 결과는 함께 나간다.
  * 카드와 제외 사유에는 검색 번호(`searchId`, 도구 호출 ID)를 붙여 화면이 검색별로 묶어 보여 줄 수 있게 한다.
* 순서는 도구 결과의 순서(코드가 정한 순위)를 따른다. LLM이 이유를 다른 순서로 써도 따르지 않는다(ADR 0004).
* LLM이 이유를 빠뜨린 카드는 `reason`이 null이다. 도구 결과에 없는 카드 ID의 이유는 버리고, 같은 카드 ID에 이유가 여러 개면 처음 것을 쓴다.
* 카드에는 실제로 쓴 환율과 그 기준일(`fxDateLabel`)을 함께 넣는다. web을 읽지 못해 대체 값을 쓴 경우에도 어느 날짜의 환율인지 보이게 하기 위해서다(ADR 0010).
* 제외 사유(`exclusions`, ADR 0004)도 같은 검색 결과에서 모은다. 같은 시술을 다시 검색했으면 마지막 검색의 제외 사유만 쓴다.
* 응답의 `cards`는 `kind`로 종류를 구분한다. 지금은 `recommendation` 하나이고, 일본 시술명 대응·예약 카드는 해당 도구 작업에서 추가한다.

비교와 재검색을 가르는 방법으로 아래를 비교했다.

| 방법 | 결과 |
| --- | --- |
| 같은 시술은 마지막 검색만 | 재검색은 맞지만, 지점·지역 비교에서 앞 대상 카드가 빠진다 |
| 같은 턴의 검색 결과를 모두 | 비교는 맞지만, 재검색에서 원하지 않은 카드가 섞인다 |
| LLM이 보여 줄 카드를 고름 | 둘 다 맞출 수 있지만, LLM이 빠뜨리면 카드가 사라지고 실행마다 달라진다 |
| LLM이 검색마다 "대신함/비교"를 표시 | 지역 외 조건의 비교도 되지만, 잘못 고르면 결과가 틀리고 실행마다 달라진다 |
| **코드가 검색 조건으로 가름(채택)** | 같은 입력에 같은 결과가 나오고 테스트로 고정된다. 지역·위치·지점이 아닌 조건(예: 일본어 되는 곳과 안 되는 곳)의 비교는 재검색으로 처리된다 |

지점 비교는 지역 비교보다 자주 생기므로 `search_clinics`에 지점 이름 검색(`clinic_name`)을 함께 추가했다(ADR 0004).

**이유**
* 금액이 틀릴 수 있는 경로를 없애는 쪽이, 틀린 뒤에 검증으로 잡는 쪽보다 단순하고 확실하다.
* 몇 곳을 어떤 순서로 보여 줄지는 코드가 정하고, 추천 이유처럼 대화 맥락이 필요한 일만 LLM에 남긴다(설계 문서 4.5, 4.7).

**후속 작업**
* 황인식·손창현 님과 카드 필드 합의(설계 문서 4.8 초안)
* T4 #7 `jpMatch`, T5 #8 `booking` 카드를 같은 방식으로 추가
* T6 #9 답변 본문 속 금액 검증. 카드는 이 방식으로 보장되지만, 답변 문장의 금액은 따로 대조해야 한다
