# [ADR-0013] 예약 연결: 채널·증빙은 web 함수 결과를 내보내고, 링크와 문장은 카드로만 낸다

* **상태 (Status):** 채택됨(Accepted). 카드 필드는 프론트(황인식·손창현 님)와 합의 필요
* **날짜 (Date):** 2026-11-27
* **관련 (Related):** T5 #8, ADR 0001·0007·0009, 설계 문서 4.7·4.8·9장·11.2, FR-05

## 1. 배경 및 문제 상황 (Context and Problem Statement)

* **상황:** 예약 채널(LINE, 카카오톡 등)은 web `clinic-channels.ts`에, 가격표 증빙 링크는 `official-proofs.ts`에, 병원용 한국어 문장은 `clinic-helpers.ts`에 TypeScript로만 있다. 문장은 두 가지다. `buildInquiryMessages`는 방문 전에 채널로 보내는 예약 문의(희망 날짜·시간대·인원, 가격 없음)이고 web 화면에서는 쓰지 않는다. `buildOrderSheetMessages`는 방문한 날 접수대에서 보여 주는 메모(시술별 공식가, 예상 합계, 부탁)이고 web 예약 시트가 보여 준다. 에이전트는 Python이고 배포에 web 소스를 넣지 않는다(ADR 0007).
* **문제:** 이것들을 어떻게 가져올지, 두 문장 중 무엇을 줄지, 예약 링크를 LLM이 답변에 쓰게 할지 정해야 한다. 설계 문서 9장은 "병원에 보낼 문의 문장", FR-05는 "접수 메모"라고 적는다. 완료 기준은 "예약 카드의 링크가 `clinic-channels` 데이터와 일치"이고, 예약·결제는 대신하지 않는다(설계 1장, FR-05).
* **목표:** 링크와 증빙이 web 화면과 같고, 같다는 것을 테스트로 확인하며, LLM이 링크를 지어내거나 잘못 옮겨 적을 수 없게 한다.

## 2. 고려한 옵션들 (Considered Options)

### 데이터 가져오기

| 방법 | 장점 | 단점 |
| --- | --- | --- |
| **web 함수 결과를 스냅샷에 넣기(채택: 채널·증빙)** | web 화면과 같은 규칙(언어별 링크 고르기, 스크린샷 숨김 규칙)을 그대로 쓴다. web 규칙이 바뀌어도 다시 내보내기만 하면 된다 | 스냅샷이 커진다(병원 137곳 × 시술별 증빙) |
| `.ts` 원본 객체만 내보내고 고르기 규칙을 Python으로 옮기기 | 스냅샷이 작다 | `getOfficialMenuProof`의 규칙(지점 우선, 가격 일치 확인, PR #22의 숨김 목록)을 따라 옮겨야 하고 어긋날 수 있다 |
| **문장 틀을 Python으로 옮기고 web 함수로 만든 기대값과 대조(채택: 두 문장)** | 날짜·시간대·인원 같은 대화 입력과 실행 중 환율로 문장을 만들 수 있다. 대조 테스트로 web과 같음을 확인한다 | web 문장이 바뀌면 Python도 고쳐야 한다(대조 테스트가 알려 줌) |
| 문장을 병원 × 시술 × 입력 조합마다 미리 만들어 내보내기 | 옮길 코드가 없다 | 날짜는 미리 만들 수 없고, 접수 메모의 엔화는 환율에 따라 바뀌며, 조합 수가 너무 많다 |

### 어느 문장을 줄까

| 방법 | 결과 |
| --- | --- |
| 문의 문장만 | 대화에서 들은 날짜·인원이 들어가지만 web 예약 시트와 문장이 다르다 |
| 접수 메모만 | web 예약 시트와 같지만 날짜·인원을 넣을 곳이 없어 방문 전 문의로는 약하다 |
| **둘 다(채택, 2026-11-27 사용자 결정)** | 방문 전 문의와 방문 당일 접수를 모두 돕는다. 접수 메모는 web 예약 시트와 같다. 카드가 길어지므로 화면 배치는 프론트가 정한다 |

| 방법 | 결과 |
| --- | --- |

| LLM에 링크를 주고 답변에 쓰게 함 | 옮겨 적다 틀릴 수 있고, 맞는지 따로 검증해야 한다 |

## 3. 결정 사항 (Decision Outcome)

* **예약 채널과 가격표 증빙은 web `getClinicChannels`·`getOfficialMenuProof` 결과를 스냅샷에 넣는다.** 내보내기 스크립트는 기존 `apps/api/scripts/export-web-snapshot.mts`를 쓴다.
  * 채널은 일본어·한국어 결과를 한 항목에 담는다(`urlJa`, `urlKo`). 두 언어의 채널 종류와 순서가 다르면 내보내기가 실패한다.
  * 증빙은 시술마다 링크·도메인·확인 날짜와, 공식 페이지 스크린샷에서 가격을 확인했는지(`hasScreenshot`, web이 스크린샷을 보여 주는 조건과 같음)를 담는다. 스크린샷 이미지 자체는 내보내지 않는다.
  * `clinic-channels.ts`, `official-proofs.ts`, `clinic-helpers.ts`, `proof-hidden.ts`(PR #22에서 추가되는 스크린샷 숨김 목록, 파일이 있을 때만)를 원본 해시 목록에 넣어, 바뀌면 `tests/test_catalog.py`가 다시 내보내라고 실패한다.
* **예약 카드에 문의 문장과 접수 메모를 둘 다 넣는다.** 두 함수를 `apps/api/src/api/domain/inquiry.py`로 옮긴다(`inquiry_messages`, `order_sheet_messages`).
  * 내보내기 스크립트가 web 함수로 기대값을 만든다. 문의 문장 48개 경우(일본어 가능·불가 병원, 시술 수, 입력 조합)는 `tests/fixtures/inquiry-expected.json`, 접수 메모 48개 경우(부가세 별도·포함 병원, 시술 수, 부탁 조합)는 `order-sheet-expected.json`이다. `tests/test_inquiry.py`가 대조한다.
  * 접수 메모는 부가세 포함·1회 기준이고 금액은 calc.py로 계산한다. 시술 하나면 합계가 병원 추천 카드의 `totalKrw`·`totalJpy`와 같다. 환율은 실행 중 환율(ADR 0010)을 쓰고 카드에 기준일을 함께 넣는다.
  * 부탁은 web 예약 시트의 기본값(추가 시술 권유 사양, 총액 먼저 확인)으로 시작한다. 사용자가 통증에 약하거나 시간이 없다고 하면 LLM이 부탁을 더한다(`order_requests`).
* **도구 `get_booking_options`는 병원 ID(`place_id`, 앞 검색 결과 `card_id`의 앞부분)를 받는다.** `card_id`를 그대로 넣어도 병원 ID와 시술로 나눠 쓴다. "첫 번째 병원"은 LLM이 앞 턴 `search_clinics` 결과의 순위로 찾는다. 날짜는 `월/일`(예: 11/28)만 받는다. LLM은 연도와 오늘 날짜를 알 수 없고, 이 형식은 한국어·일본어 문장 어디에 넣어도 읽힌다. 앞 0과 공백은 지우고 없는 날짜(2/30)는 오류로 돌려준다. "내일"처럼 계산이 필요한 날짜는 넣지 않고 묻는다. 이름(여권 영문명)은 받지 않고 문장에 빈칸으로 남긴다(설계 6장 개인정보).
* **채널 링크와 두 문장은 예약 카드(`kind: booking`)로만 낸다.** LLM이 받는 도구 결과에는 채널 이름("LINE", "Naver Booking")과 접수 메모 합계만 있고 URL과 문장 본문은 없다. 시스템 프롬프트와 도구 설명에 예약·결제를 대신하지 않는다고 적는다.
* **병원 추천 카드에 후기 평점(`rating`, 근거 `ratingScope`·`ratingTier`), 예약 채널(`bookingChannels`), 가격표 증빙(`proof`)을 붙인다(설계 4.7 "보여 주기").** 후기 수는 web 데이터에 없어 넣지 않는다.
* 카드 조립은 ADR 0009를 따른다. 이번 턴의 성공한 결과만 쓰고, 같은 병원을 두 번 부르면 마지막 결과 한 장이다(자리는 처음 부른 순서). 카드 순서는 `jp_match` → `location` → `recommendation` → `booking`이다. 병원을 보여 준 뒤 예약으로 가는 흐름(설계 11.2)과 같다.

**이유**
* 링크가 데이터와 다를 수 있는 경로를 없애는 쪽이, 답변 속 링크를 검증하는 쪽보다 단순하고 확실하다(ADR 0009와 같은 이유).
* 고르기 규칙이 있는 데이터는 web 함수 결과를 받는 쪽이 web 화면과 어긋나지 않는다. 문장 틀처럼 대화 입력이 필요한 것만 옮기고 대조 테스트로 묶는다(ADR 0007과 같은 방식).

**후속 작업**
* PR #22(web 동기화)가 `official-proofs.ts`를 바꾸고 `proof-hidden.ts`를 추가한다. 머지되면 해시 대조 테스트가 실패하므로 `pnpm --filter @repo/api export:web-data`를 다시 돌린다. 그때 `proof-hidden.ts`도 해시 목록에 들어간다
* 황인식·손창현 님과 예약 카드·추천 카드 필드 합의. 인스타그램 핸들 표시(`handleText`)와 증빙 스크린샷 파일은 내보내지 않았다
* 접수 메모의 부탁을 화면에서 켜고 끄는 기능(web 예약 시트의 칩)은 프론트가 정한다
