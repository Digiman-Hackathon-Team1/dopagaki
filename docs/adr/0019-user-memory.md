# [ADR-0019] 사용자 기억은 응답 칸으로 받아 코드가 검사·저장하고, 그 턴 사용자 메시지에 안내로 붙인다

* **상태 (Status):** 채택됨(Accepted)
* **날짜 (Date):** 2026-11-28
* **관련 (Related):** T26 #71, ADR 0003·0005·0006·0015·0018, 설계 문서 v1.11(4.8·8장·9장·10장)

## 1. 배경 및 문제 상황 (Context and Problem Statement)

* **상황:** 설계 FR-12(P1)는 사용자가 말한 조건(예산·귀국일·위치·고민 등)을 프로필에 저장하고, 다음 날 새 대화에서 다시 묻지 않게 하라고 한다. 설계 9장은 저장을 `save_preference` 도구로 적었다. 지금 에이전트는 대화 기억만 있고(`InMemorySaver`), 시스템 프롬프트와 도구 정의 19,003토큰을 프롬프트 캐싱으로 모든 대화가 같이 쓴다(ADR 0015, `docs/test/2026-11-28-prompt-caching.md`).
* **문제:**
  * 저장을 도구로 하면 Claude가 "저장해 달라"고 응답한 뒤 다시 불러야 답이 나온다. 검색이 없는 턴("모레요"처럼 질문에만 답하는 턴)은 호출이 1번에서 2번이 된다. 측정값으로 호출 1번은 약 +$0.0005, +2.2초다(바로 답한 대본 $0.0007·4.9초, 검색 후 답한 대본 $0.0012·7.1초의 차이).
  * 사용자별 값을 시스템 프롬프트에 넣으면 캐시가 사용자마다 갈라진다.
  * "모레 귀국"을 다음 날 쓰려면 절대 날짜로 바꿔 저장해야 하는데, Claude는 오늘 날짜를 모른다.
  * 사용자 저장소를 정할 DB가 아직 없다. #53(카탈로그 DB)에는 사용자 테이블이 없고, 설계 15장의 메모리 저장소 종류는 이우진·박준석 님이 정할 항목이다.
* **목표:** 첫 글자가 나오는 시간을 늘리지 않고, 캐시를 깨지 않으며, 사용자가 직접 말한 조건만 저장한다.

## 2. 고려한 옵션들 (Considered Options)

### 1. 저장 방식

* **A. `save_preference` 도구 (설계 9장 그대로):** 검색이 있는 턴은 검색 도구와 같이 불러 호출이 늘지 않는다. 검색 없는 턴만 호출이 1번 늘어 그 턴의 답이 약 2.2초 늦어진다.
* **A'. 답과 저장 호출을 한 응답에 받고, 저장 결과는 다음 턴 메시지 앞에 붙이기:** API 규칙상 도구 결과 뒤에 새 사용자 글을 이어 붙일 수 있다(Anthropic 문서 handle-tool-calls, 실제 요청 본문으로 확인). 그러면 추가 호출이 0번이다.
* **C. 응답 칸 끝에 `remember`(기억할 조건) 칸을 두고 코드가 저장:** 추가 호출이 없다. 칸 출력 30~80토큰(약 $0.00003, 추정)만 늘어난다. 답 본문 뒤 칸이라 화면에 흘려보내는 답은 늦어지지 않는다(`service.py`의 `_AFTER_ANSWER`).
* **B. 답을 보낸 뒤 별도의 짧은 Claude 호출로 조건을 뽑기:** 첫 글자 지연은 없지만 호출 경로·프롬프트·비동기 처리가 하나 더 생긴다.
* **D. 검색 도구 입력에서 코드가 뽑기:** 비용이 0이지만 검색 없는 턴은 저장하지 못하고, Claude가 넣은 기본값(사용자가 말하지 않은 '여행자' 등)까지 저장된다.

**A·A' 실험 (Haiku 5.5, 앱과 같은 시스템 프롬프트·도구·응답 형식·effort, 2026-11-28, 9번 호출, 약 $0.009)**

| 상황 | 결과 |
| --- | --- |
| 검색 없이 조건만 답함 (한국어 3번, 일본어 3번) | 6번 모두 답만 하고 저장 도구를 부르지 않음. 답과 저장이 한 응답에 온 경우 0번 |
| 검색이 있는 턴 (3번) | 2번은 검색과 저장을 한 응답에 같이 부름(저장 값 정확). 1번은 대본 문제(도쿄 지명)로 되물음 |

* 지시 한 단락으로는 A'이 되지 않았다. A도 검색 없는 턴에서 저장을 빠뜨릴 수 있다.

### 2. 기억 안내를 붙이는 곳과 턴

* **시스템 프롬프트:** 사용자마다 앞부분이 달라져 캐시가 갈라진다. 채택하지 않는다.
* **그 턴 사용자 메시지 블록, 매 턴:** 구현이 단순하다. 50턴이면 기록이 약 5K 토큰 늘고, 대화 중 바꾼 조건과 예전 안내가 기록에 섞인다.
* **그 턴 사용자 메시지 블록, 대화 첫 턴과 저장 내용이 바뀐 뒤 첫 턴:** 토큰이 가장 적고 충돌이 적다. 마지막에 붙인 안내를 상태에 둬야 한다.
* **대화 첫 턴만:** 대화 중 다른 탭에서 바꾸거나 지운 내용이 반영되지 않는다.

### 3. 상대 날짜

* **코드 계산 + 오늘 날짜 안내:** `remember`가 "며칠 뒤"(0=오늘, 2=모레)와 날짜 중 하나를 받는다. 며칠 뒤는 코드가 서울 날짜로 계산한다. 매 턴 안내에 오늘 날짜(약 15토큰)를 붙여 "11월 30일", "화요일"도 받는다.
* **코드 계산만:** 지금 `plan_trip`과 같다. 요일 표현은 받지 못한다.
* **오늘 날짜 안내만:** Claude가 날짜 계산을 틀릴 수 있다.

### 4. 저장소

* **서버 메모리 + 인터페이스:** 지금 쓸 수 있다. 재배포·재시작하면 사라지고, 서버가 여러 개면 공유되지 않는다(대화 기억과 같은 한계).
* **지금 DB 테이블 만들기:** #53이 머지되지 않았고 Railway PostgreSQL 적용이 확인되지 않았다. 저장소 종류는 설계 15장에서 이우진·박준석 님이 정한다.

## 3. 결정 사항 (Decision Outcome)

* **선택한 옵션:**
  * **저장은 C안이다.** `AgentReply` 맨 끝에 `remember` 칸을 둔다. 화면(`ChatResponse`)에는 보내지 않는다. 무엇을 저장할지는 Claude가 고르고, 검사와 저장은 코드가 한다(ADR 0005의 역할 분담과 같다). `save_preference` 도구는 만들지 않는다.
  * **코드 검사:**
    * 사용자가 이 대화에서 직접 말한 값인지 대조한다. 예산 금액은 사용자 본문 금액에 있어야 하고, 일본에서 받은 시술은 사용자 본문에 있는 글이어야 하며, 위치는 이 대화에서 찾은 위치 ID여야 한다. 어긋난 칸은 오류로 돌리지 않고 저장하지 않는다. 오류로 돌리면 Claude가 다시 시도해 호출이 는다.
    * 날짜·방문 유형·바늘 기피는 대조할 수 없어 형식과 범위만 본다(오늘 이후 1년 안, 도착일 ≤ 귀국일).
    * 건강 정보는 자유 글 칸(일본에서 받은 시술)만 키워드(`safety.mentions_health`)로 거른다. 나머지 칸은 정해진 값·숫자·날짜·위치 ID라 건강 정보가 들어갈 자리가 없다.
    * 크기 상한: 고민 3개, 일본에서 받은 시술 3개 × 40자.
  * **저장 항목:** 설계 8장의 7개에 예산 범위(시술 1회 / 전체, 말하지 않았으면 비움)를 더한다. 병원 검색 예산은 1회, 일정 예산은 전체라 같은 3만 엔이 다르게 쓰이는 것을 막는다.
  * **불러오기:** `load_context`가 사용자 ID(그래프 설정 `configurable.user_id`, LLM이 넣지 않음)로 프로필을 읽는다. 대화 첫 턴과 저장 내용이 바뀐 뒤 첫 턴에, 그 턴 사용자 메시지에 `[본문, 기억 안내, 언어 안내]` 순서로 붙인다. 지난 메시지는 고치지 않는다. 안내에는 저장된 날짜까지 며칠 남았는지 코드가 계산해 적고, 귀국일이 지난 체류 기간은 넣지 않는다. 기억은 빠진 정보만 채우고, 이번 턴에 말한 조건이 우선한다(설계 4.2).
  * **금액 검사:** 기억 안내에 있는 금액도 답에 쓸 수 있게 `amounts.known_amounts`가 기억 안내 블록을 금액 출처로 본다. 지금은 사용자 메시지의 첫 블록만 본다.
  * **저장소:** `api/domain/profile.py`에 `ProfileStore` 인터페이스와 서버 메모리 구현을 둔다. 전체 잠금 하나로 칸 단위로 합치고, 같은 칸은 나중 값이 이긴다. 마지막 저장 뒤 30일(저장할 때마다 다시 30일)이 지나면 지우고, 사용자 1만 명을 넘으면 오래된 것부터 지운다. DB 구현은 15장 결정 뒤 같은 인터페이스로 추가한다.
  * **보기·지우기 API:** `GET`·`DELETE /api/agent/users/{userId}/profile`. 전체 지우기만 둔다. 저장된 게 없어도 GET은 빈 프로필로 200, DELETE는 204다.
  * **50턴 상한:** LLM을 부르지 않으므로(ADR 0018) 대화 중 이미 저장된 조건만 새 대화로 이어진다.
* **채택하지 않은 옵션:** A·A'(실험에서 검색 없는 턴 저장 0/6), B(구현량), D(직접 말한 조건만 저장한다는 원칙과 어긋남), 시스템 프롬프트에 기억 넣기(캐시).

**이유**
* 첫 글자 지연 0초, 추가 호출 0번이다. A의 검색 없는 턴 +2.2초를 없앤다.
* `remember`는 응답 형식의 칸이라 구조화 출력이 매 응답에 칸이 있음을 보장한다. 빈 값으로 둘 수는 있어도 도구 호출처럼 통째로 건너뛰지는 못한다.
* 기억 안내를 그 턴 사용자 메시지에 붙이고 기록을 덧붙이기만 하므로 캐시 앞부분(도구 + 시스템)이 모든 사용자에게 같다.

## 4. 결과 및 영향 (Consequences)

* **장점:**
  * 사용자 기억이 응답 시간과 캐시 적중률에 주는 영향이 칸 출력 30~80토큰으로 끝난다(추정, 구현 뒤 측정).
  * 저장소를 인터페이스로 감싸 DB로 바꿀 때 그래프와 API를 고치지 않는다.
* **단점 및 위험:**
  * 응답 형식(`AgentReply`)과 시스템 프롬프트가 바뀌어 배포 때 캐시 앞부분이 한 번 다시 쓰인다. 측정 문서의 19,003토큰 수치도 달라진다.
  * 서버 메모리라 재배포·재시작하면 기억이 사라지고, 서버가 여러 개면 공유되지 않는다.
  * 보기·지우기 API는 대화(`/chat`)처럼 익명 UUID만 알면 누구나 부를 수 있다. 저장 내용에 건강 정보는 없다.
  * Haiku가 `remember`를 비워 두는 비율은 실제 테스트로 확인해야 한다.
  * 화면 위치(헤더 버튼과 아래 시트)와 지운 뒤 새 대화 확인은 황인식·손창현 님과 맞출 항목이다.
* **후속 작업:**
  * T26 #71 구현과 Haiku 실제 테스트(새 대화에서 예산·귀국일을 다시 묻지 않음)
  * 설계 15장 메모리 저장소 종류 결정 뒤 DB 구현(이우진·박준석 님)
