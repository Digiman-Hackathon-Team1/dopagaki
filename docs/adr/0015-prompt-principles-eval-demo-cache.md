# [ADR-0015] 상호작용 원칙 프롬프트·시나리오 평가·데모 응답 캐싱

* **상태 (Status):** 채택됨(Accepted)
* **날짜 (Date):** 2026-11-27
* **관련 (Related):** T7 #10, ADR 0003·0006·0014, 설계 문서 2장·4장·13장·15장(v1.6)

## 1. 배경 및 문제 상황 (Context and Problem Statement)

* **상황:** 설계 4장의 상호작용 원칙(답이 먼저, 질문 묶음, 조건 요약, 범위 3단계, 기억으로 요청을 바꾸지 않음, 말투)이 시스템 프롬프트에 없었다. 시스템 프롬프트에는 도구 순서, 금액 규칙, 안전 정지 규칙만 있었다. 기본 모델은 Haiku 5.5로 정했다(설계 15장, v1.5).
* **문제:**
  * 지금 프롬프트로 Haiku를 시나리오 7개에 돌리면 원칙이 지켜지지 않았다. 아래 "개선 전" 결과다.
    * 병원을 보여 주면서 질문 묶음 2개를 함께 냈다. 설계는 답 뒤에 질문을 하나만 덧붙인다.
    * "얼굴 처짐"처럼 고민만 들은 첫 턴에 회복 기간을 묻지 않고 바로 검색했다.
    * 다음 질문 제안을 사용자에게 묻는 문장으로 썼다(예: "ソウルに行く日程はいつ頃ですか？", 서울에 가는 일정은 언제쯤인가요?).
    * 주변 질문(시술 후 세안)에 도파가키 데이터가 아니라는 말 없이 답했다.
    * 일본어 답변에 한국어 병원 이름이 섞였다(예: "밴스의원 홍大店").
  * `search_clinics`의 `japanese_only`(일본어 가능 병원만)를 LLM이 실행마다 다르게 넣었다. 같은 여행자 질문에 한 번은 넣지 않아 일본어 상담이 안 되는 병원이 나왔고, 다른 턴에는 `false`를 넣었다. 설계 4.3은 위치를 답하기 전에는 일본어 가능 병원을 우선하고, 여행자는 일본어가 필요하다고 본다. 4.7은 "일본어(여행자)"를 거르기 항목에 둔다.
  * 설계 13장은 LLM이 사용자 역할을 맡아 대화를 자동으로 돌리게 했다. 사용자 역할 호출이 턴마다 더 들고, 대화가 매번 달라져 프롬프트를 고치기 전과 후를 비교하기 어렵다. API 크레딧이 개발 이틀 만에 바닥난 상황이다.
  * 시연 때 네트워크나 Claude가 느리면 화면이 멈춘다. 설계는 "데모 시나리오 응답을 캐시해 현장 네트워크 문제에 대비"한다고만 정했다(2장, 13장).
* **목표:** 원칙을 시스템 프롬프트로 옮기고, 같은 대본으로 고치기 전과 후를 비교해 결과표로 남긴다. 시연은 정한 대본에서 Claude 없이도 같은 답을 내게 한다.

## 2. 고려한 옵션들 (Considered Options)

### 일본어 상담 가능 여부

#### 1. 여행자는 일본어 가능 병원만 보여 준다(설계 4.3·4.7)

도구 입력을 빠뜨리면 코드가 일본어 가능 병원만 찾고, 거주자나 한국어 상담도 괜찮은 사용자에게만 LLM이 끈다.

**Pros**
* LLM이 입력을 빠뜨려도 결과가 같다.
* 일본어로 상담하지 못해 예약에서 막히는 병원을 보여 주지 않는다.

**Cons**
* 더 싼 병원이 있어도 사용자는 모른다. 리쥬란은 병원 112곳 중 59곳이 일본어 상담을 하지 않는다. 일본어 가능 병원만 보면 2위가 ₩108,900(밴스의원 발산점)에서 ₩148,500(밴스의원 명동점)으로 바뀐다.
* 사용자가 이름을 말한 지점이 일본어 상담을 하지 않으면 빠져, 따로 예외를 둬야 한다.

#### 2. 위 방식 + 빠진 더 싼 병원을 한 줄로 알림

**Pros**
* 일본어 가능 병원을 지키면서 더 싼 곳이 있다는 것은 알린다.

**Cons**
* 사용자가 한 번 더 물어야 전체를 본다. 프롬프트 지시를 LLM이 빠뜨릴 수 있다.

#### 3. 거르지 않고 절약액 순으로 모두 보여 주고, 카드로 구분한다

**Pros**
* 최우선 가치인 일본 대비 싼 가격(4.7)을 그대로 보여 준다.
* 병원 카드에는 이미 `japaneseSupport`가 있어 화면이 되는 곳과 안 되는 곳을 구분할 수 있다.
* LLM이 입력을 빠뜨려도 결과가 같다(기본이 거르지 않음).

**Cons**
* 일본어 상담이 안 되는 병원이 1위에 올 수 있다. 화면 구분과 추천 이유로 알린다.
* 설계 4.3·4.7을 바꿔야 한다.

### 시나리오 평가 방식

#### 1. 고정 대본 + 코드 채점 + 사람 판정

사용자 말을 시나리오마다 미리 적어 두고 차례로 보낸다. 도구 선택, 도구 입력, 답변 속 금액, 질문 묶음·병원 카드 유무, 안전 정지는 코드가 채점한다. 원칙 준수(답이 먼저, 말투, 범위 응답)는 사람이 대화 기록을 읽고 판정한다.

**Pros**
* 같은 대본이라 고치기 전과 후를 비교할 수 있다.
* 에이전트 몫의 호출만 든다(시나리오 7개, 에이전트 11턴, Haiku 17~20번).

**Cons**
* 사용자가 대본에 없는 말을 하는 경우는 보지 못한다.
* 원칙 준수 판정이 자동이 아니다.

#### 2. LLM이 사용자 역할 + LLM 판정(설계 13장)

**Pros**
* 대화 흐름이 다양해져 대본에 없는 경우도 본다.

**Cons**
* 사용자 역할과 판정 호출이 한 바퀴에 약 20번 더 든다.
* 대화 길이와 내용이 매번 달라 비교가 어렵다.

### 데모 응답 캐싱

#### 1. 서버 녹화본, 대본에서 벗어나면 실제 Claude가 이어 답함

대본을 실제 Claude로 한 번 돌려 턴마다 응답과 대화 기록을 녹화한다. `AGENT_DEMO_CACHE=1`이면 새 대화의 메시지가 대본과 같은 동안 녹화 응답을 돌려준다. 대본과 다른 메시지가 오면 녹화한 대화 기록을 대화 기억에 넣고 실제 Claude가 이어 답한다.

**Pros**
* 시연 중 즉흥 질문에도 앞 맥락(보여 준 병원 등)을 이어 답한다.
* 대본 안에서는 API 키나 네트워크가 없어도 답한다.

**Cons**
* 녹화한 thinking 블록은 프롬프트가 바뀌면 받아들여지지 않으므로(ADR 0006) 빼고 넣어야 한다.

#### 2. 서버 녹화본, 벗어나면 시세표 안내

**Pros**
* 구현이 단순하다.

**Cons**
* 대본에서 한 마디만 달라도 시연이 끊긴다.

#### 3. 화면(web)에서 캐싱

**Cons**
* web 담당 영역이고, 서버의 대화 기억과 어긋난다.

## 3. 결정 사항 (Decision Outcome)

* **일본어 상담 가능 여부로 거르지 않고 절약액 순으로 보여 주며, 카드의 `japaneseSupport`로 화면이 구분한다(3안).** `japanese_only`는 기본 false이고, 사용자가 일본어 상담이 되는 곳만 원한다고 말했을 때만 LLM이 true를 넣는다. 추천 이유에는 일본어 상담 가능 여부를 적는다. 설계 4.3(위치·일본어 기본값)과 4.7(거르기 항목에서 일본어를 보여 주기로)을 바꿨다(설계 v1.6). 화면 표시는 web 담당과 맞춘다.
* **4장 원칙을 시스템 프롬프트의 "How to reply / Scope / Wording" 세 묶음으로 넣는다.** 기존 금액 규칙과 안전 정지 문장은 그대로 둔다. 턴마다 바뀌지 않는 고정 문장이라 thinking 블록 조건(ADR 0006)을 해치지 않는다.
  * 답이 먼저: 시술명을 들으면(일본 시술명은 `match_jp_treatment`로 찾은 뒤) 바로 검색해 답하고, 결과를 더 맞출 질문은 answer 끝에 하나만 쓰며 questions는 비운다. 병원을 거를 수 있는 조건(회복 기간이 있는 시술이면 귀국일, 아니면 숙소)을 먼저 묻는다.
  * 먼저 묻기: 고민만 있고 회복 가능 기간을 모를 때, 고민도 시술도 없을 때는 검색하지 않고 질문 2~3개를 묶어 묻는다. 도구 규칙의 먼저 묻기(일본 시술명 후보가 여러 개, 위치를 못 찾음, 예약할 병원이 불분명)도 그대로 둔다. 안전 정지 규칙이 "답이 먼저"보다 앞선다고 적었다.
  * 조건 요약에는 쓴 기본값까지 적고, 모르는 조건과 약한 근거는 주의사항에 적는다. 앞 대화는 빠진 정보를 채우는 데만 쓴다.
  * 범위: 주변 질문은 일반 정보라고 밝히고 원래 주제로 돌아오며, 범위 밖은 한 문장으로 거절하고 할 수 있는 일을 말한다.
  * 말투: 프롬프트의 예시는 한국어 대신 영어로 쓰고 "답변 언어로"를 붙인다. 한국어 예시가 일본어 답변에 한국어가 섞이는 것을 부추길 수 있어서다. 일본어 답변에는 모든 칸에서 일본어 병원·시술 이름을 쓰고, 도구 결과의 영어 표기(incl. VAT 등)는 답변 언어로 옮긴다. 카드 이유는 도구 결과의 사실만 쓰고, 다른 카드와 비교하는 말은 같은 검색의 모든 카드에 대해 맞아야 한다. 다음 질문 제안은 사용자 말투로 쓴다.
  * T6에서 본 "검색한다고 하고 도구를 안 부름"을 막으려고, 도구를 쓰기로 했으면 같은 응답에서 부르고 "찾아볼게요"로 끝내지 않는다고 적는다.
* **도구 설명과 응답 칸 설명을 같은 원칙으로 맞춘다.** `recommend_treatments`는 회복 가능 기간을 모르면 부르지 않고 먼저 묻는다. `questions`는 먼저 물을 때만, `suggestions`는 사용자 말투로 쓴다.
* **시나리오 평가는 고정 대본 + 코드 채점 + 사람 판정으로 한다**(`apps/api/scripts/eval_scenarios.py`). 모델이 Haiku가 아니면 실행하지 않는다. LLM 사용자 역할과 반복 안정성(pass^3)은 모델을 다시 비교할 때 검토한다.
* **데모 캐싱은 서버 녹화본으로 하고, 대본에서 벗어나면 실제 Claude가 이어 답한다**(`api/agent/demo.py`, `scripts/record_demo.py`).
  * 대본 비교는 앞뒤 공백, 전각·반각, 끝 문장부호를 무시한다.
  * 이미 대본과 무관하게 진행 중인 대화는 대본이 가로채지 않는다. 한 번 벗어난 대화는 끝까지 실제 Claude가 답한다.
  * 녹화 응답은 하루 한도에 세지 않고, API 키가 없어도 대본 안에서는 답한다. 키가 없으면 대화 기억을 볼 수 없어, 대본이 처음 보는 대화 ID는 모두 새 대화로 본다.
  * 녹화본이 잘못되면(파일 형식, 녹화 뒤 바뀐 응답 형식) 로그를 남기고 실제 경로로 답한다. 데모 때문에 일반 대화가 실패하지 않게 하기 위해서다.
  * 대본 진행 상태는 서버 메모리에 대화 1000개까지 두고, 넘으면 오래된 것부터 잊는다. 같은 대화로 요청이 동시에 오는 경우는 다루지 않는다(대기열은 T9 #13).
  * 녹화한 대화 기록을 넣을 때 thinking 블록을 뺀다. Haiku 5.5가 thinking 블록을 뺀 앞 턴을 받아들이는 것을 실제 호출로 확인했다.

**이유**
* 일본어 상담 여부는 사용자가 카드를 보고 직접 고를 수 있는 정보라, 코드가 미리 빼는 것보다 보여 주는 쪽이 최우선 가치(싼 가격)에 맞다. 기본이 "거르지 않음"이라 LLM이 입력을 빠뜨려도 결과가 같다.
* 같은 대본으로 비교해야 프롬프트 변경의 효과를 숫자로 볼 수 있고, 비용 제약 안에서 반복할 수 있다.
* 시연에서는 대본 밖 질문이 나올 수 있어, 벗어나도 맥락을 잇는 쪽이 낫다.

**검증 (Haiku 5.5, 2026-11-27)**

Haiku 호출 수는 대화 기록에 남은 응답 수다. 빈 응답을 다시 요청한 호출은 세지 않아 실제보다 적을 수 있다.

| 실행 | 프롬프트 | 코드 채점 통과 | Haiku 호출 |
|---|---|---|---|
| 1 | 개선 전 | 4/7 | 20 |
| 2 | 4장 원칙 추가 | 6/7 (실패 1건은 채점기가 도구 기본값을 보지 않은 오류) | 18 |
| 3 | 금액 표기·질문 하나·카드 비교 규칙 추가 | 7/7 | 17 |
| 4 | 이름 섞임·같은 가격 규칙 추가 (s3만) | 1/1 | 5 |

**남은 약점** (프롬프트로 줄였지만 없애지 못함)
* 일본어 답변에 한국어 병원 이름이 가끔 섞인다(실행 4 뒤 녹화 확인에서도 "밴스의원 홍대점（バンス医院 弘大店）"이 나왔다).
* 카드 이유에 데이터에 없는 추측이 가끔 붙는다(예: "명동 호텔가 근처라 이동이 편할 수 있어요").

**후속 작업**
* T9 #13: 시스템 프롬프트와 도구 설명을 캐시 대상으로 만든다. 이번 변경으로 시스템 프롬프트가 길어졌다.
* 데모 대본이 정해지면 `scripts/record_demo.py`로 녹화하고 녹화본을 커밋한다.
