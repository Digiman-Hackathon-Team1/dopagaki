# [ADR-0005] 코드와 LLM의 역할 분담

* **상태 (Status):** 채택됨(Accepted)
* **날짜 (Date):** 2026-11-26
* **관련 (Related):** T1 #4

## 1. 배경 및 문제 상황 (Context and Problem Statement)

* **상황:** 에이전트는 가격, 절약액, 예약 링크, 시술 데이터를 다루면서 동시에 사용자의 말을 해석하고 설명한다. web 순위표에도 같은 가격과 절약액이 나온다.
* **문제:** LLM이 금액이나 링크를 직접 만들면 같은 질문에 다른 숫자가 나오거나 web 화면과 숫자가 어긋날 수 있다. 반대로 모든 판단을 코드로 짜면 사용자 표현의 다양함을 다루지 못한다.
* **목표:** 무엇을 코드가 정하고 무엇을 LLM이 정하는지 한 기준으로 나눠, 도구와 프롬프트를 만들 때마다 다시 논의하지 않게 한다.

## 2. 고려한 옵션들 (Considered Options)

### 1. 매번 같아야 하는 것은 코드, 상황에 따라 달라도 되는 것은 LLM

매번 같은 값이 나와야 하거나 다른 화면과 일치해야 하는 것은 코드(도구)가 정하고, 상황에 따라 달라도 되는 것은 LLM이 정한다(설계 문서 4.5).

| 코드가 정함 | LLM이 정함 |
| --- | --- |
| 가격, 엔화 환산, 절약액 | 말투, 설명 방식 |
| 예약 채널 링크 | 다음에 무엇을 물을지 |
| 회복 기간, 바늘 여부 같은 시술 데이터 | 어떤 도구를 언제 부를지 |
| 고민 → 시술 연결 (고민별 시술표) | 사용자 표현 → 고민 해석 (정해진 6개 분류 또는 "지원하지 않음") |
| 병원과의 거리 (좌표 계산) | 일반 지식 답변 |
| 추천 순서 (절약액 정렬) | 추천 이유 설명 |

**Pros**
* 금액과 링크가 web 화면과 항상 같다.
* 금액은 도구 결과와 대조해 검증할 수 있다(설계 문서 12장 숫자 검증).
* 도구를 가짜 LLM 없이 단위 테스트할 수 있다.

**Cons**
* 데이터에 없는 정보(영업시간, 요일 한정가 등)는 코드로 정할 수 없어 데이터를 따로 준비해야 한다.

### 2. LLM이 데이터를 읽고 직접 계산·추천

데이터를 프롬프트나 도구 결과로 통째로 넘기고, 계산과 순서까지 LLM이 정한다.

**Pros**
* 도구를 적게 만들어도 된다.

**Cons**
* 같은 질문에 다른 금액과 순서가 나올 수 있고, web 순위표와 어긋난다.
* 틀린 금액을 찾아내기 어렵다.

## 3. 결정 사항 (Decision Outcome)

* **매번 같아야 하는 것은 코드, 상황에 따라 달라도 되는 것은 LLM이 정한다.**
* **LLM이 데이터를 읽고 직접 계산·추천하는 방식은 채택하지 않는다.**

**이유**
* 최우선 가치가 일본 대비 싼 가격이라 금액이 틀리면 서비스가 성립하지 않는다.
* web 순위표와 같은 숫자를 보여 줘야 한다.
* 사용자 표현 해석과 대화 진행은 코드로 다 다룰 수 없어 LLM이 맡는다. 단 해석 결과는 정해진 분류 안에서만 고르게 해 코드가 이어받을 수 있게 한다.
