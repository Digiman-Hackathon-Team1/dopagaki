# [ADR-0001] 에이전트 데이터 경로: web 데이터를 JSON 스냅샷으로 읽기

* **상태 (Status):** 채택됨(Accepted)
* **날짜 (Date):** 2026-11-26
* **관련 (Related):** T0 #3

## 1. 배경 및 문제 상황 (Context and Problem Statement)

* **상황:** 병원·가격·예약 채널 데이터는 지금 web에만 있다(`apps/web/src/data/prices.json`, `clinic-channels.ts` 등 `.ts` 파일). 백엔드 DB는 이우진 님이 만들고 있고, 아직 완성 시점과 스키마가 정해지지 않았다.
* **문제:** 에이전트 P0(11/27 점심 PoC)는 실제 병원 데이터로 추천·검색·예약 연결을 보여 줘야 한다. DB에 예약 채널과 가격표 증빙이 들어갈지도 아직 정해지지 않았다.
* **목표:** DB 완성을 기다리지 않고 web 순위표와 같은 숫자로 에이전트를 만들고, DB가 생기면 에이전트 코드 대부분을 그대로 쓴다.

## 2. 고려한 옵션들 (Considered Options)

### 1. web 데이터를 JSON 스냅샷으로 내보내 읽기

web의 데이터 파일을 JSON 스냅샷으로 내보내고, 에이전트는 데이터 조회 계층을 거쳐 스냅샷을 읽는다.

**Pros**
* P0 일정 안에 실제 데이터로 시연할 수 있다.
* web 순위표와 같은 원본을 쓰므로 화면끼리 숫자가 맞는다.
* DB가 생기면 조회 계층의 구현만 바꾸면 된다.

**Cons**
* web 데이터가 바뀌면 스냅샷을 다시 내보내야 한다.
* web 데이터 파일을 다루므로 프론트 담당(황인식)과 공유가 필요하다.

### 2. 백엔드 DB 완성까지 대기

DB와 조회 API가 준비된 뒤 에이전트가 DB를 읽는다.

**Pros**
* 데이터 원본이 처음부터 하나다.

**Cons**
* P0 일정(11/27 점심)을 맞추지 못한다.
* DB에 예약 채널과 가격표 증빙이 들어갈지 정해지지 않아, 들어가지 않으면 FR-05(예약 연결)를 만들 수 없다.

## 3. 결정 사항 (Decision Outcome)

* **web 데이터를 JSON 스냅샷으로 내보내 읽는다.**
* **백엔드 DB 조회는 DB가 준비되면 조회 계층의 구현으로 교체한다.**
* **DB 완성까지 대기하는 방식은 채택하지 않는다.**

**이유**
* P0 일정 안에 실제 데이터로 시연해야 한다.
* web 순위표와 같은 원본을 써야 절약액이 화면끼리 맞는다(설계 문서 4.7).
* 조회 계층을 두면 DB 전환 때 도구와 그래프 코드는 바뀌지 않는다.
