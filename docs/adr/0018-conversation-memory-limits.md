# [ADR-0018] 같은 대화 요청은 대화별 잠금으로 줄 세우고, 대기 초과·턴 상한은 오류 대신 안내 응답으로 답한다

* **상태 (Status):** 채택됨(Accepted)
* **날짜 (Date):** 2026-11-28
* **관련 (Related):** #13, #46, #49, PR #58, ADR 0006·0014, 설계 문서 8장 대화 기억 관리

## 1. 배경 및 문제 상황 (Context and Problem Statement)

* **상황:** 대화 기억은 서버 메모리(`InMemorySaver`)에 있다. 같은 대화 ID로 요청이 겹치거나, 대화가 길어지고 쌓이는 것을 막는 장치가 없었다.
* **문제:**
  * 답을 기다리는 중에 사용자가 메시지를 또 보내면 두 요청이 같은 대화 기록을 동시에 읽고 쓴다. 한 턴이 기록에서 사라지거나 순서가 꼬일 수 있다.
  * 대화 수와 한 대화의 길이에 상한이 없어 서버 메모리가 계속 늘고, 긴 대화는 요청마다 입력 토큰이 늘어난다.
  * 설계 8장은 "최대 60초 기다리고 넘으면 409"였다. 그런데 스트리밍(`/chat/stream`, #49)은 응답을 시작하면 HTTP 상태를 바꿀 수 없다. 백엔드 구조 규칙(PR #58)도 스트리밍 실패는 `done`의 안내로 보낸다고 정했다.
* **목표:** 같은 대화의 요청은 순서대로 처리하고, `/chat`과 `/chat/stream`이 같은 방식으로 답하게 한다.

## 2. 고려한 옵션들 (Considered Options)

### 1. 대기 시간(60초)을 넘겼을 때

* **두 입구 모두 안내 응답(`fallback: "busy"`)**: HTTP 200에 시세표 안내와 같은 형식으로 "앞 메시지에 아직 답하는 중"을 알린다. 화면 처리가 한 가지다. 설계 8장의 409를 바꾼다.
* **`/chat`만 409, 스트림은 안내 응답**: 설계는 그대로지만 입구마다 화면 처리가 다르다.
* **두 입구 모두 409**: 스트림도 응답 시작 전에 잠금을 잡아야 해서 router가 잠금을 다뤄야 한다. "router는 서비스만 부른다"(PR #58)와 어긋난다.

### 2. 잠금을 둘 곳

* **`ChatService`의 시작 처리(`_begin`)**: 두 입구가 같이 쓰는 곳이라 한 번만 쓴다. 스트림은 generator 안에서 잡고 `finally`에서 풀어, 연결이 끊겨도 풀린다.
* **router 의존성**: 입구마다 따로 써야 하고 스트림의 잠금 수명을 응답과 맞추기 어렵다.

## 3. 결정 사항 (Decision Outcome)

* **선택한 옵션:**
  * 대기 초과는 두 입구 모두 `fallback: "busy"` 안내 응답으로 답한다.
  * 한 대화 50턴을 넘으면 LLM을 부르지 않고 `fallback: "turn_limit"`(새 대화를 열라는 안내)으로 답한다. 대기 초과와 턴 상한은 하루 한도에 세지 않는다.
  * 잠금과 보관은 `service.py`의 `Conversations`가 맡는다. 마지막 요청 뒤 24시간이 지난 대화와, 1000개를 넘은 가장 오래된 대화를 요청이 끝날 때마다 대화 기억에서 지운다. 처리 중이거나 기다리는 요청이 있는 대화와 방금 끝난 대화는 지우지 않는다.
  * 스트림은 잠금을 기다리기 전에 `start`를 보낸다.
* **선택 이유:** 기다리면 풀리는 상황이라 클라이언트 오류(4xx)로 볼 일이 아니다. 두 입구가 같은 응답 모델로 답하면 web이 `fallback` 값 하나로 처리한다.

## 4. 결과 및 영향 (Consequences)

* **장점:**
  * 같은 대화의 두 턴이 모두 순서대로 기록에 남는다(pytest로 `/chat`·`/chat/stream` 각각 확인).
  * 서버 메모리의 대화 수가 상한을 넘지 않는다.
* **단점 및 위험:**
  * 잠금은 서버 프로세스 메모리에 있어, 서버를 여러 개 띄우면 서버끼리는 줄 세우지 못한다. 저장소를 DB로 바꿀 때 같은 규칙을 다시 정한다(설계 8장).
  * 기다리는 요청은 서버 스레드 하나를 최대 60초 잡는다.
  * web은 `busy`·`turn_limit`을 아직 따로 그리지 않고 일반 실패 문구를 보인다. 상담 화면 작업에서 맞춘다.
  * 데모 녹화 응답의 진행 상태(`DemoSessions`)는 이 보관 규칙 밖에 있다.
