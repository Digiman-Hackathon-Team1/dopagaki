# [ADR-0008] 문서와 작업 운영: 노션은 설계, 레포는 구현, 이슈와 todo-task 스킬로 작업

* **상태 (Status):** 채택됨(Accepted)
* **날짜 (Date):** 2026-11-26
* **관련 (Related):** T0 #3

## 1. 배경 및 문제 상황 (Context and Problem Statement)

* **상황:** 에이전트 설계는 노션 설계 문서 v1.0에 있고, 팀원과 운영진도 노션을 본다. 작업은 GitHub 이슈(T0~T8)로 나눴고, 코딩 에이전트(Claude Code 등)로 구현한다.
* **문제:** 설계·구현·작업 규칙이 어디에 있는지 정하지 않으면 같은 내용이 여러 곳에 적히고 서로 어긋난다. 코딩 에이전트마다 읽는 규칙 파일 이름도 다르다(`AGENTS.md`, `CLAUDE.md`).
* **목표:** 문서마다 원본을 하나로 정하고, 코딩 에이전트가 이슈를 골라 같은 절차로 작업하게 한다.

## 2. 고려한 옵션들 (Considered Options)

### 1. 노션은 설계, 레포는 구현 문서. 이슈와 todo-task 스킬로 작업

- 노션: 설계와 결정 근거
- 레포: 구현된 내용(`apps/api/src/api/agent/README.md`), 작업 규칙(`AGENTS.md`), 결정 기록(`docs/adr/`)
- 작업 규칙의 원본은 `AGENTS.md`다. `CLAUDE.md`는 `@AGENTS.md` 한 줄로 불러오기만 한다.
- 작업 설명은 이슈 본문(목표·범위·완료 기준·의존)에 둔다. `todo-task` 스킬이 이슈를 읽어 작업을 시작한다.

**Pros**
* 팀원·운영진이 보는 노션을 그대로 설계 원본으로 쓴다.
* 규칙을 `AGENTS.md` 한 곳에서만 고치면 된다.
* 이슈가 작업 설명과 진행 상황을 함께 담아 따로 동기화할 것이 없다.

**Cons**
* 설계를 바꾸면 노션과 영향받는 이슈를 함께 고쳐야 한다.

### 2. 설계 문서를 레포로 옮기기

노션 설계 문서를 레포의 Markdown으로 옮겨 코드와 함께 관리한다.

**Pros**
* 설계 변경이 코드 리뷰를 거친다.

**Cons**
* 팀원과 운영진이 보는 노션과 멀어진다.
* 남은 기간에 옮기는 비용이 든다.

### 3. one-tatchi의 tasks.md 동기화까지 도입

one-tatchi-platform처럼 `docs/tasks.md`에 작업 계획을 두고, 동기화 스크립트·워크플로로 이슈와 체크박스를 맞추고 Slack으로 알린다.

**Pros**
* 작업 계획 전체를 한 파일에서 볼 수 있다.

**Cons**
* 남은 기간(본선 11/29)에 비해 스크립트·워크플로·Slack 설치 비용이 크다.
* 작업 설명의 원본이 노션, 이슈, `tasks.md` 셋이 된다.

## 3. 결정 사항 (Decision Outcome)

* **노션은 설계, 레포는 구현 문서로 나누고, 이슈와 `todo-task` 스킬로 작업한다.**
* **설계 문서를 레포로 옮기는 방식은 채택하지 않는다.**
* **`tasks.md` 동기화 장치는 도입하지 않는다.** `todo-task` 스킬만 가져와 이슈 기준으로 고친다.

**이유**
* 설계 원본은 팀원과 운영진이 보는 노션에 있어야 한다.
* 작업 설명의 원본은 이슈 하나로 충분하다. 남은 기간에 동기화 장치를 설치·유지할 이유가 없다.
* 규칙 파일을 `AGENTS.md` 하나로 두면 코딩 에이전트가 바뀌어도 규칙은 그대로다.

**구성**
* `CLAUDE.md`(루트, `apps/api`): `@AGENTS.md`
* `apps/api/AGENTS.md`: 에이전트 작업 규칙 섹션
* `.agents/skills/todo-task/SKILL.md`: 스킬 원본. `.claude/skills/todo-task`는 이 폴더를 가리키는 심볼릭 링크다.
