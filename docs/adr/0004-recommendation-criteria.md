# [ADR-0004] 추천 기준: 거르기 → 일본 대비 절약액 정렬, 가중치 점수 없음

* **상태 (Status):** 채택됨(Accepted)
* **날짜 (Date):** 2026-11-26
* **관련 (Related):** T2 #5, 설계 문서 4.5·4.7·9장

## 1. 배경 및 문제 상황 (Context and Problem Statement)

* **상황:** `search_clinics`는 시술 하나를 받아 병원 상위 몇 곳을 고른다. 고를 때 쓸 수 있는 값은 가격, 일본 대비 절약액, 거리, 후기 평점, 일본어 가능, 회복 기간, 바늘 여부, 예산이다.
* **문제:** 이 값들로 순서를 정하는 방법과, 절약액의 기준이 되는 한국·일본 가격을 정해야 한다. 에이전트가 web 순위표와 다른 숫자나 다른 순서를 보이면 사용자가 어느 쪽을 믿어야 할지 모른다.
* **목표:** 최우선 가치(일본보다 싼 가격)를 지키고, 같은 조건이면 web 순위표와 같은 숫자·순서가 나오며, 순서를 사용자에게 설명할 수 있게 한다.

## 2. 고려한 옵션들 (Considered Options)

### 1. 거르기 → 기준 하나로 정렬 → 나머지는 표시만

조건에 맞지 않는 병원은 뺀다. 남은 병원을 기준 하나(기본은 일본 대비 절약액)로 정렬한다. 거리·후기·가격 조건은 카드에 표시만 한다.

**Pros**
* web 순위표의 기본 정렬(절약액 순)과 같은 순서가 나온다.
* "일본 평균보다 ¥51,819 싸서 1위"처럼 순서를 한 문장으로 설명할 수 있다.
* 정렬 기준을 바꿔 달라는 요청(가까운 순, 후기 순)을 기준만 바꿔 처리한다.

**Cons**
* 조금 비싸지만 아주 가까운 병원은 절약액 순에서 뒤로 밀린다. 다음 질문 제안("가까운 곳 순으로 보여 줘")으로 보완한다.

### 2. 가중치 점수

절약액, 거리, 후기 평점에 가중치를 곱해 더한 점수로 정렬한다.

**Pros**
* 여러 값을 한 번에 반영한다.

**Cons**
* 가중치를 정할 근거가 없다.
* 왜 그 순서인지 설명하기 어렵고, web 순위표와 순서가 달라진다.

### 3. LLM이 순서를 정함

도구는 후보만 주고 Claude가 순서를 고른다.

**Pros**
* 대화 맥락을 반영할 수 있다.

**Cons**
* 같은 질문에도 순서가 달라진다. 순서는 코드가 정하고 LLM은 이유를 설명한다는 설계 원칙(4.5)에 어긋난다.

## 3. 결정 사항 (Decision Outcome)

* **거르기 → 기준 하나로 정렬 → 나머지는 표시만 하는 방식을 선택한다.**
* **가중치 점수와 LLM 순위 결정은 채택하지 않는다.** 시나리오 테스트에서 이상한 추천이 나오면 그때 기준을 추가한다.

| 역할 | 항목 |
| --- | --- |
| 거르기 | 회복 기간·바늘(시술 단위), 지역·일본어·예산(병원 단위). 안전은 그래프 노드 `safety_check`가 맡는다 |
| 정렬 | 기본 `savings`(절약액 큰 순). 요청하면 `distance`(가까운 순, 기준 위치 필요) 또는 `rating`(후기 평점 순) |
| 표시 | 거리, 가격 조건(태그와 문장), 가격 출처, 거르기로 빠진 병원 수(사유별). 후기·예약 채널·증빙은 T5 이후 |

정렬 동률 처리는 web `buildRankedRows`와 같다.

| 정렬 | 비교 순서 |
| --- | --- |
| savings | 절약액 큰 순 → 거리 가까운 순 |
| distance | 거리 가까운 순 → 부가세 포함 가격 싼 순 |
| rating | 후기 평점 높은 순 → 절약액 큰 순 → 거리 가까운 순 |

### 절약액 계산

* 한국 가격은 항상 부가세 포함이다. 병원 표시가가 부가세 별도(`vatExcluded`)이고 시술에 부가세가 붙으면(`vatAppliesInKorea`) 10%를 더한다.
* 일본 가격은 시술마다 일본 주요 5개 병원의 세금 포함 공식가 평균(`jpBenchmarkJpy`)이다. web 순위표와 같은 기준이다. 카드에는 평균과 함께 범위(최저·최고)와 병원 수를 넣는다.
* 환율은 web과 같은 네이버 환율 스냅샷(100엔당 원)이다.
* 절약액(엔) = 일본 평균 − 한국 가격(부가세 포함)의 엔화 환산. 반올림은 JavaScript `Math.round`와 같게 한다.
* 가격 조건(첫 방문 한정, 이벤트가, 마취비 별도 등)은 절약액 계산에 넣지 않는다. 조건별 금액이 데이터에 없기 때문이다. 카드에는 문장과 함께 태그로 표시한다.
* 태그는 `api/domain/price_tags.py`가 병원 문장(`caveatKo`)과 가격 메모(`noteKo`)를 규칙으로 분류해 붙인다. 태그는 `first_visit`(첫 방문·체험가), `event`(이벤트가·특가), `day_limited`(요일 한정), `app_benefit`(앱·카카오 혜택가), `anesthesia`(마취비 별도·확인), `extra_fee`(시술 팁 별도) 6개다. 부가세 별도는 계산에서 이미 더하므로 태그로 보지 않는다. LLM으로 분류하지 않는 이유는 같은 데이터에 매번 같은 태그가 붙어야 하기 때문이다(설계 문서 4.5).

### 제외 사유

* 거르기로 빠진 병원은 사유별 병원 수로 응답의 `exclusions`에 담는다(설계 문서 9장, FR-03). 사유는 `needle`·`downtime`(시술 전체가 빠짐), `area`, `japanese`, `budget`이다.
* 한 병원이 여러 조건에 걸리면 처음 걸린 사유 하나로 센다. 순서는 지역 → 일본어 → 예산이다.
* 예산 비교는 부가세 포함 가격으로 한다. 엔 예산은 엔화 환산 값, 원 예산은 원화 값과 비교한다.

**이유**
* 최우선 가치가 일본 대비 싼 가격이고, 정렬 기준이 하나면 그 가치가 순서에 그대로 드러난다.
* web 순위표와 같은 계산·같은 동률 처리를 써야 화면끼리 숫자와 순서가 맞는다.
* 기준을 하나로 두면 순서를 설명할 수 있다.
