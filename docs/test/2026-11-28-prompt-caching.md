# 프롬프트 캐싱 전후 측정 결과 (Haiku 5.5)

- 작업: T23 [#59](https://github.com/Digiman-Hackathon-Team1/dopagaki/issues/59) 프롬프트 캐싱으로 상담 비용·첫 글자 대기 시간 줄이고 전후 측정
- 날짜: 2026-11-28
- 모델: `claude-haiku-5-5` (effort `medium`, max_tokens 16000)
- 기준 문서: 노션 설계 문서 8장 "대화 기억 관리"의 비용, 6장 응답 시간
- 실행 스크립트: [`apps/api/scripts/measure_turn_cost.py`](../../apps/api/scripts/measure_turn_cost.py)

## 1. 요약

- 상담 한 턴의 **입력 비용이 86% 줄었다**($0.00384 → $0.00053). 출력까지 합친 턴당 비용은 $0.00444 → $0.00115(74% 감소)다. 이 값은 도구 정의와 시스템 프롬프트가 이미 캐시에 있는 상태 기준이다. 5분 넘게 요청이 없다가 오는 대화는 첫 호출에서 이 앞부분을 캐시에 새로 쓰는 비용을 낸다(5장, 추정 약 58% 감소).
- 적용 후 입력 토큰의 **97%를 캐시에서 읽었다**. 2턴째 이후 첫 호출과 한 턴 안 두 번째 이후 호출은 모두(100%) 캐시에서 읽었다.
- **첫 글자 시간과 전체 시간은 줄었다고 확인하지 못했다.** 중앙값 차이(0.2~0.3초)가 같은 조건 안의 흔들림(1~10초)보다 훨씬 작다.
- LLM 호출마다 붙는 앞부분(도구 정의 + 시스템 프롬프트 + 응답 형식)은 실제로 19,003 토큰(약 19.0K)이다. 첫 호출의 입력 약 19.1K는 여기에 첫 사용자 메시지가 더해진 값이다.

## 3. 측정 방법

- **첫 글자 시간**: 요청을 보낸 때부터 첫 `delta` 이벤트까지. `delta`가 없는 턴은 전체 시간으로 둔다(이번 측정에는 없었다).
- **전체 시간**: 요청을 보낸 때부터 `done` 이벤트까지.
- **토큰 수**: 대화 기억에 남은 응답(`AIMessage.usage_metadata`)에서 LLM 호출마다 읽는다. langchain-anthropic의 `input_tokens`는 Anthropic `input_tokens`(캐시 제외)에 캐시 읽기와 캐시 쓰기를 더한 전체 입력이다. 그래서 캐시 없이 처리한 입력 = 전체 − 캐시 읽기 − 캐시 쓰기로 계산한다.
- **입력 비용**: (캐시 없이 처리한 입력 × 1 + 캐시 쓰기 5분 × 1.25 + 캐시 쓰기 1시간 × 2 + 캐시 읽기 × 0.1) × $0.10 / 100만 토큰. 출력은 $0.50 / 100만 토큰. Haiku 5.5의 프롬프트 10만 토큰 이하 단가다.
- **캐시 적중률**: 캐시에서 읽은 토큰 / 전체 입력 토큰.
- **p90**: nearest-rank 방식(40개 중 36번째 값).
- **채점**: 턴마다 `eval_scenarios.py`의 `grade_turn`으로 채점해, 캐싱 전후 답의 동작이 같은 수준인지 본다.

## 5. 해석

- **비용**: 모든 시나리오에서 입력 비용이 86% 줄었다. 출력 비용은 캐싱과 관계없어 그대로다. 캐싱 후에는 출력 비용이 입력 비용보다 크다.
- **첫 글자 시간**: 줄었다고 확인하지 못했다. 같은 조건의 같은 대본에서도 1초에서 10초까지 흔들려, 반복 5번으로는 0.2~0.3초 차이를 가를 수 없다. 원인은 추정이다. 앞부분 19K 토큰을 읽는 시간보다 도구 호출과 출력(thinking 포함)을 만드는 시간이 훨씬 길어, 캐싱으로 줄어든 시간이 드러나지 않는 것으로 본다. 첫 글자는 에이전트가 도구를 다 부른 뒤 답을 쓰기 시작할 때 나온다.
- **적용 후 측정은 앞부분이 이미 캐시에 있는 상태였다**: 적용 후 76개 호출 중 도구 정의·시스템 프롬프트(19,003 토큰)를 캐시에 새로 쓴 호출은 없다. 캐시 쓰기 48,753 토큰은 모두 대화 뒷부분이다. 반복 1의 첫 호출은 몇 분 전에 돌린 실제 Claude 테스트(`test_live_prompt_cache_reads_within_and_across_turns`)가 써 둔 캐시를 읽었다. 반복 2~5는 대본의 첫 사용자 메시지가 매번 같아 그 메시지까지 캐시에서 읽었다.
- **캐시가 비어 있을 때(추정, 측정하지 않음)**: 도구 정의와 시스템 프롬프트는 모든 대화가 같으므로, 배포본에서도 5분 안에 어느 사용자든 요청이 이어지면 캐시가 살아 있다. 5분 넘게 요청이 없다가 새 대화가 오면, 첫 호출이 19,003 토큰을 1.25배 단가로 캐시에 쓴다. 캐시에서 읽을 때보다 대화당 약 $0.0022가 더 든다. 이번 대본 같은 2턴 대화라면 턴당 입력 비용은 약 $0.0016으로, 적용 전보다 약 58% 적다. Claude를 한 번만 부르고 끝나는 대화는 캐싱 전보다 약 25% 비싸다.
- **채점**: 적용 전·후 측정 때는 채점 실패 이유를 기록하지 않았다(이유를 남기는 기능은 그 뒤 커밋 `fe75682`에서 넣었다). 이유를 남긴 s5 추가 5번(10턴 중 실패 5턴)은 모두 "건강 정보를 화면 칸에 씀"이었다. 전·후 측정의 s5 실패도 같은 이유로 추정한다. Claude가 "妊娠中は必ず担当の医師に確認してください"(임신 중에는 반드시 담당 의사에게 확인하세요) 같은 문장을 주의사항 칸에 썼다. 앱은 이 문장을 화면에 보내기 전에 걸러 낸다(`graph.py`의 `screen_reply`). 그래서 화면에는 나오지 않고, Claude가 지시를 어긴 것만 채점에 잡힌다. 캐싱을 넣은 상태로 s5만 5번 더 돌렸을 때 5/10이어서, 적용 후의 9/10은 우연한 차이로 본다.

## 6. 적용한 캐싱

- 캐시 표시를 두 곳에 붙인다(`graph.py`의 `build_graph`).
  - 시스템 프롬프트 끝: 요청은 도구 → 시스템 → 메시지 순으로 읽히므로, 이 표시가 도구 정의와 시스템 프롬프트를 함께 캐시한다.
  - 요청 전체(자동 캐싱): 마지막 블록에 표시가 붙어 호출마다 뒤로 옮겨 간다. 한 턴 안의 도구 호출 반복과 다음 턴 모두 앞 호출까지의 대화 기록을 캐시에서 읽는다.
- 유지 시간은 기본 5분이다. 캐시를 읽을 때마다 다시 5분으로 늘어나므로 대화가 이어지는 동안은 계속 읽힌다. 쓰기 비용은 5분이 입력 단가의 1.25배, 1시간이 2배다.
- `AGENT_PROMPT_CACHE=0`이면 표시를 붙이지 않는다(기본 1).
- 캐시를 깨는 값은 앞부분에 없었다. 옮긴 코드는 없다.
  - 시스템 프롬프트는 고정 문자열이고 날짜·시각이 없다.
  - 도구 목록은 고정된 순서의 리스트이고, 도구 설명은 import 때 한 번 만들어진다.
  - 응답 언어 안내와 안전 안내는 그 턴 사용자 메시지 끝에 LLM을 부르기 전에 붙고, 대화 기록에 그대로 남는다. 지난 메시지를 다시 고치지 않는다.
  - effort와 응답 형식(`output_config`)은 요청마다 같다.
  - 이 점들은 `tests/test_agent_prompt_cache.py`가 확인한다. 도구 호출, 다음 턴, 응답 언어 변경, 건강 키워드 안내가 섞인 3턴에서, 앞 호출의 요청 본문이 다음 호출 요청 본문의 앞부분인지 본다.
